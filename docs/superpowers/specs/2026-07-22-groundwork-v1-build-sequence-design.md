## The organizing insight

The three candidate starting points — `scripts/validate.py`, `demo/`, `interview/` — are not independent. They are all **consumers of one thing that does not yet exist as files: the schema.** Every CONTEXT.md decision is a *shape* (ontology tiers #5, Owner's Card spine #6, memory frontmatter #7, proposal schema #17, version pin #21, demo canon #16). The validator *checks* that shape; the demo *instantiates* it; the interview *generates* it. Each candidate, started whole and alone, fails differently:

- **Validator alone → inert.** A checker with nothing to check passes vacuously; a correct checker is indistinguishable from a broken one. (The wwf5d dead-path / corpus-void trap — a scan that scans nothing ships looking done.)
- **Demo alone → too big.** A complete synthetic company depends on *every* schema at once — maximum surface, zero checker feedback.
- **Interview alone → premature.** The generator produces content in the schema's shape; building it before the target shape is hand-proven means authoring a machine for an artifact never made once.

**Resolution: build one vertical slice (a walking skeleton).** One function, all the way down — schema-as-files + a filled demo instance + the validator checks that govern exactly those files — then repeat horizontally, then build the generator, then honesty-gate the outward docs.

## Dependency order (the spine → consumers)

1. **Schema-as-files** (the grammar): ontology worksheet template, work-package spec, Owner's Card template, org-memory schema, constitution/governance templates → `ontologies/ skills/ governance/`.
2. **`scripts/validate.py`** — co-developed; each schema file gets its checks in the same slice (can't trust a shape without a check, can't write a check without a shape).
3. **One demo function slice** — the end-to-end vertical proof.
4. **Rest of `demo/`** — horizontal repetition.
5. **`interview/`** — the generator, now that the output shape is proven.
6. **`delivery/` + `docs/` + README capability claims** — honesty-gated, last.
7. **Root files** (`AGENTS.md`, one-line `CLAUDE.md`) — D2 Move 2, at the Phase 1→2 boundary.

Under #10 a company OS *is* the root of its own repo, so its files carry repo-relative paths; if `demo/` is to be the shape the generator writes `your-company/` in, it must carry exactly those paths. It also stops a demo skill borrowing an engine exemplar by climbing out — the demo has to be a complete company, not a folder using this one's homework.

- **2026-07-28 — Slice 2.3a landed + merged to `main`** (`1cd13f1`, pushed). `_instance_roots` plus five checks converted to per-instance loops; the 1.5d-ii nested-root deferral closed. 572 tests, engine output held at exactly `0 error(s), 7 warning(s)` in both modes, and the five-check SILENT probe fired on every converted check. **Codex ran three rounds.** Round 1 found three real BLOCKING holes in the conversion — `superseded_by` resolving against the root instead of the record's instance; the baseline allowlist reloading `.gitignore` from the nested instance, so a root-ignored record could still satisfy the provisioning gate; and a *dangling* content-dir symlink no longer marking an instance, silently losing the symlink ERROR. When a repair picks a path component, ask which one and why — first-vs-last is not a detail.

- **Memory ownership decided (Slice 2.3b, maintainer call surfaced 2026-07-28):** 2.3a left containment **asymmetric** — a root skill could cite `baseline: demo/memory/x.md` (because `_memory_record_files(root)` walks every nested `memory/`), while the reverse was blocked. **Resolved: close it symmetrically** — *a memory record belongs to exactly one instance, the parent of the last `memory` component in its path, and only that instance may cite it.* Fable recommended leaving it because nothing exercised it; that argument expires the moment `demo/` holds records (2.3c), at which point an engine exemplar could take its baseline from the fictional company's numbers and the provisioning gate would be satisfied by invented data. Cheap because 2.3a already computes exactly that rule for supersession after two review rounds — it gets extracted to `_memory_instance_base` and gains a second consumer. **One rule, one home, two consumers** is what makes "belongs to exactly one instance" true rather than merely intended. Counter-argument recorded: it forecloses a shared memory pool, which #10's one-company-one-repo model does not sanction anyway.

- **Canon shape (Slice 2.3b):** `demo/canon.md` carries the machine-readable allowlist in #11 frontmatter (`domains`, `external_domains`, `phone_range`) and the fictional world in prose — #16's "one file that is both human documentation and machine-checked truth", the same pattern as the #9 manifest and the #18 proposal file. **`external_domains` ships empty on purpose:** without a declared escape hatch, the first legitimate link to something real creates pressure to loosen the check, which is how a positive allowlist dies; with one, the demo starts at zero real domains and any addition is a visible, reviewable edit to the file that documents the world.
